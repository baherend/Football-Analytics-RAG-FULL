## Architecture Decisions

- **Competition portability via `ArtifactPaths`, not per-competition branching**: `src/artifacts.py` centralizes all dataset-scoped paths; WC2022 keeps a legacy flat-layout exception (`legacy_default=True`) so zero-argument calls stay unchanged, but `ArtifactPaths` itself makes no competition-ID special cases.
- **Embedding model selection via a small registry, not scattered literals**: `src/embedding_config.py::EmbeddingModelConfig`/`resolve_embedding_config()` replaced four independently hardcoded `"all-MiniLM-L6-v2"` strings. Dense-index identity is tied to embedding-model identity through `ArtifactPaths.chroma_collection_name` (suffixed only when non-default, so existing collection names are unchanged for the default model).
- **Structural split of the old `06_retrieve_context.py`** into `src/retrieval/search.py` (BM25/Dense/RRF/safeguards/context-building) and `src/query/router.py` (intent classification + structured/semantic/hybrid execution) — mechanical extraction, no behavior change, done in two phases (A: new modules created alongside the old file; B: callers migrated, old file deleted).
- **`rag/` must not depend on `knowledge/` internals** (corrected in the architecture contract after initial drafting): `knowledge/` produces indexes/stores; `rag/` consumes them only through stable storage/index-access contracts declared in `infrastructure/`. `infrastructure/` carries technical contracts only, never football business logic, though it may reference `domain/` types. `domain/football/` remains the lowest project-specific layer (depends on nothing, everything else may depend on it). See `docs/architecture/overview.md` §4–5.
- **One canonical architecture document, not two**: root `ARCHITECTURE.md` was replaced with a compatibility pointer rather than being independently corrected, to avoid maintaining two competing descriptions going forward.
- **Arabic retrieval support is safeguard-layer, not embedding-layer**: MSA/Egyptian comparison intent detection lives in `src/retrieval/safeguards.py` (re-exported from `search.py`) as parallel phrase/regex sets to the existing English ones, deliberately not a language-detection or translation layer; team-style detection moved to `src/team_style.py` in Phase 5 but is the same kind of layer. Entity names stay in canonical Latin form by design; Arabic-script entity transliteration is explicitly out of scope for that layer.
- **Phase 7 — `hybrid_search()` CANNOT move to `src/orchestration/`; it stays in `src/retrieval/search.py` (assessment only, no code changed)**. Re-measured after Phase 4 made `hybrid_search()` thin (it is now just `select_relevant_chunks(hybrid_candidates(q, k), k)`). The blocker is not the function body — it is that **every** route out requires a layer to import `src.orchestration`, which the committed Phase B1 contract `test_runtime_layers_do_not_import_orchestration` forbids for `src/retrieval`, `src/query`, `src/context`, `src/generation`, `src/verification`, `src/knowledge`, and `src/evaluation` — i.e. all of them:
  - `retrieve_context()` stays in `search.py` and calls `hybrid_search()` as a bare global ([search.py:357](src/retrieval/search.py#L357)) → `search.py` would import orchestration. **Forbidden.**
  - `src/query/router.py` calls it at two sites → `query → orchestration`. **Forbidden.**
  - `src/evaluation/retrieval_evaluator.py` binds `retrieval_fn = retrieval_module.hybrid_search` where `retrieval_module = import_module("src.retrieval.search")` (also `bm25_search`, `dense_search`, `CHROMA_DIR`, and both caches from that same module object). Either the protected harness changes, or `search.py` keeps a re-export — and the re-export itself requires `search.py` to import orchestration. **Forbidden either way.**
  - Keeping a compat re-export purely to satisfy the above would make the shim the only reason the architecture looks clean — the explicitly rejected outcome, and the same trap as Step 2's deleted `service.py`.
  - **The move also would not close the `retrieval → context` edge**: `search.py` still imports `build_context` for `retrieve_context()` ([search.py:373](src/retrieval/search.py#L373)) regardless. The claimed architectural gain is smaller than it appears.
  - No import *cycle* would be raised at runtime (the `orchestration → verification → src.query.query_schema` chain lands on a leaf dataclass module), so this is a **layering-contract** violation, not an `ImportError`. Already machine-enforced — no new guard test was needed.
  - **Prerequisite before this is reconsidered**: the evaluator's "one retrieval module owns hybrid_search + bm25_search + dense_search + CHROMA_DIR + both caches" contract, and `retrieve_context()`'s residence in `search.py`. Until those move, `search.py` legitimately owns `hybrid_search()`.
- **Phase 5 — team-style classification is shared vocabulary, not a layer's property**: `src/team_style.py` is a flat neutral module (same convention as `src/stage_taxonomy.py`, `src/embedding_config.py`, `src/artifacts.py`) owning `_detect_team_style_query`/`_detect_team_style_entities`, their `_STYLE_KEYWORDS`/`_STYLE_KEYWORDS_AR` vocabularies, and the shared `_normalize_arabic_for_matching`/`_extract_latin_entity_spans`/`_LATIN_ENTITY_SPAN` text helpers. It imports **only `re`** — no layer, no I/O, no chunk store.
  - **Why not `src/query/`**: `src/retrieval/safeguards.py::_ensure_team_style_doc()` uses the same detectors, so moving them under `query/` would just have reversed the arrow into `retrieval → query`. Both layers now depend *downward* on shared vocabulary instead of sideways on each other. `src/domain/` was explicitly not created — no other domain concepts exist yet, and one file does not justify a new namespace layer.
  - **`_normalize_arabic_for_matching` travelled with the classifier** even though it is a general Arabic matching helper, because it is shared by exactly two callers — the moved `_detect_team_style_entities()` and the *staying* `_detect_comparison_entities()`. Leaving it in `safeguards.py` would have forced `team_style → retrieval`, defeating the move; duplicating it would let the two copies drift. `safeguards.py` imports it back. If more shared text helpers accumulate, they belong in a dedicated text-matching module rather than growing `team_style.py` — noted in that module's docstring.
  - **Surviving `query → retrieval` edge is legitimate**: `router.py` still imports `hybrid_search` — that is *execution* calling the RETRIEVE stage, which follows the runtime flow. Only classification was reversed, and `tests/test_team_style_boundary.py` pins that distinction (19 tests: direction, purity, single definition, call-site identity, behavior).
- **Chunk selector is now Unicode-aware but the real corpus is English-only**: `src/context/selection.py`'s tokenizer (was `src/retrieval/chunk_selector.py`) recognizes Arabic script, proven correct via synthetic-content tests, but has zero measured effect on the current benchmark because every chunk's `text` field and every entity-metadata field in this dataset is English/Latin-only — confirmed by direct inspection (0/6594 chunks contain Arabic).
- **Verification discipline**: every phase in this project's history has followed baseline → competing hypotheses → evidence → surgical patch → targeted verify → regression → RAG evaluation → security → review, with an explicit final commit-safety verdict. This is now formalized in `AGENT_RULES.md`.
- **Migration Step 2 (Retrieval Split), mechanical split inside `src/retrieval/`, not a `rag/` namespace move yet**: `src/retrieval/search.py`'s BM25/Dense/RRF/safeguards were split into `bm25.py`/`dense.py`/`fusion.py`/`safeguards.py`. **`search.py` is now `src/retrieval/`'s transitional compatibility boundary, not a final architecture module** — it stays as a re-export layer, and also still holds index loading and `hybrid_search()` orchestration (see below), until a future phase can retire it entirely. Rejected moving to a new top-level `rag/` package this phase — no other target packages (`domain/`, `knowledge/`, `infrastructure/`) exist yet, so a lone `rag/retrieval/` would be a premature, half-built namespace.

Keeping `hybrid_search()` physically in `search.py` needs no lazy-import trick: it resolves `bm25_search`/`dense_search`/etc. as bare names via its own module's globals, exactly as it always did, and is monkeypatch-compatible for free. `service.py` was deleted rather than kept as an empty stub.
  - **Context-building** (`build_context`/`retrieve_context`) stays in `search.py` because it's a distinct future responsibility (Migration Step 4) that must not be folded into retrieval.
  - **Removal plan**: `search.py` retires once a future phase (a) updates `reset_retrieval_caches()` and the direct-monkeypatch tests to target `bm25.py`/`dense.py`/`safeguards.py` directly instead of `src.retrieval.search`, at which point (b) index loading moves to its own module and (c) `hybrid_search()` moves into a real `service.py`/`rag/retrieval/service.py`, resolving its dependencies via normal top-level imports with no reverse coupling. Not scheduled — this is a marker for when it becomes safe, not a commitment to a specific future step.

- **Migration Step 4 (Context Engineering / Evidence Pack), new top-level `src/context/` package**: evidence selection and presentation moved out of retrieval. `retrieval/chunk_selector.py` → `context/selection.py`, `retrieval/answerability.py` → `context/answerability.py` (both `git mv`, content byte-identical), `search.py::build_context()` → `context/rendering.py`, plus a new `context/evidence.py`. `src/retrieval/__init__.py`'s exports of the moved symbols were dropped rather than shimmed — nothing outside the package imported them.   - **`EvidencePack` is real, minimal, and lossless.** `EvidencePack.from_chunks()` keeps each original candidate dict verbatim on `EvidenceItem.raw`, and `to_chunks()` returns *those same objects* (identity-checked in tests) — so citations, prompt text, and answerability receive byte-identical input, making the pack a pure representation addition with provably zero behavior change. It guarantees provenance (`chunk_id`/`document_id` per item) and exposes `entity_coverage`. Consumers today: `execute_route()` (builds the pack for the SELECT EVIDENCE → ANSWERABILITY handoff and returns it on `RoutedResult.evidence`) and `rendering.render_pack()`. Fields with no populator/consumer were deliberately omitted.
  - **Stages deliberately NOT built, on measured evidence**: **Deduplicate** — candidate-pool duplicate count measured **0 across all 8 baseline cases** because retrieval's safeguards already dedupe by `chunk_id`; a dedup stage would be a no-op box. **Token budget** — one already exists implicitly (`max_chunks` count + `max_length` characters); no token-aware need proven. **Compression** — `DEFERRED, NOT YET JUSTIFIED`: no demonstrated budget overflow, no consumer, no way to evaluate information loss.

So the same evidence can render differently per interface. Unifying them changes generation semantics → belongs to Migration Step 5.

## Security Findings

- **ReDoS, found and fixed** (Arabic safeguards phase): `_detect_comparison_entities()` had 3 vulnerable regex shapes (2 pre-existing English patterns — `X vs Y`, `X or Y` — plus 1 new Arabic pattern) that combined `re.search()`'s per-position retry with an unbounded quantifier, producing O(N²) behavior on long non-matching input (100k-character payloads hung >60s). Fixed by bounding every entity-capturing quantifier to 60 characters; verified sub-second on the same payloads afterward. 8 permanent regression tests protect this.
- **SQL/shell/path/Chroma-filter injection**: repeatedly, adversarially tested across the retrieval safeguard layer and the chunk selector — confirmed inert in all cases. Query text and extracted entities only ever reach `.lower()`/substring comparisons, embedding vectors, or fixed-shape `{"level": ...}` Chroma filters; never raw SQL, shell commands, or filesystem paths. No SQL is constructed anywhere in the retrieval path (Chroma's own SQLite usage is internal to its parameterized API).
- **ReDoS in the router's comparison patterns — found and FIXED**: `src/query/intent.py::COMPARISON_PATTERNS`' `(\w+)\s+vs\.?\s+(\w+)` and `(\w+)\s+versus\s+(\w+)` had **unbounded** entity quantifiers; with `re.search()`'s per-position retry (no fixed literal prefix to fast-scan for) this was O(N²) on any long run of word characters — a consistent 4.0× per doubling, reaching 16.5 s on 20 KB of accented text (`é` is `\w` in Python 3, so never ASCII-only), reachable from user query text via `classify_query()` on *every* query. It was the **missed twin** of the same shape fixed earlier in `src/retrieval/safeguards.py::_detect_comparison_entities()`; the router held an independent copy. Proven pre-existing (identical timings against `git show HEAD:src/query/router.py`), not caused by the Step 3 split. **Fixed** by bounding both to `(\w{1,60})` — chosen on evidence, not copied: `\w` matches neither spaces nor hyphens, so these patterns only ever captured a single token, and the longest single `\w` token across all 713 corpus entity names is 14 chars (`Dayotchanculle`), leaving >4× headroom while matching safeguards.py's convention. Now linear (exactly 2.0× per doubling; 20 KB accented 16.5 s → 0.034 s, 484× faster; 100 KB `classify_query` ≈ 0.17 s). 32 permanent tests in `tests/test_query_intent_security.py` pin the complexity property (wall-clock bound + a doubling-ratio scaling guard + a structural "no bare `(\w+)`" check) and the unchanged comparison behavior. Other comparison patterns re-probed with their own literal prefixes: worst 0.067 s at 40 KB, no residual pathology.

- **ReDoS in `extract_numeric_claims()` — found and FIXED**: three of the five claim patterns in `src/verification/validation.py` began with an unbounded lazy entity capture `(\w[\w\s]*?)`. `[\w\s]` matches letters, digits, underscores and whitespace — i.e. almost any prose — so with `re.finditer()` retrying at every position and the span expanding toward end-of-string for a literal that never appears, work was O(N²). Measured ~4.0× per doubling: 2 KB 0.094 s → 8 KB 1.44 s → 16 KB 15.8 s → 40 KB ~159 s. Reached on every structured/hybrid answer via `validate_structured_answer()` → `validate_answer()`, and the input is **LLM output** (attacker-influenceable: evidence can steer a model into long number-dense text; a hostile provider response is fully attacker-controlled). Per-pattern attribution showed the other two patterns already linear (one gates its trailing capture behind a literal prefix, one captures no entity) and they were left untouched. **Fixed** by bounding the three leading captures to `_MAX_ENTITY_SPAN = 200`. The bound is evidence-chosen, **not** copied from the 60 used in `intent.py`/`safeguards.py` — those capture a single `\w` token, whereas this span can include a whole sentence prefix; the measured worst realistic capture (longest corpus name, 46 chars, behind a long prefix) is 109 chars, so 200 leaves ~83% headroom, and K≥120 produced **zero** output differences across 2570 realistic claim sentences built from real corpus names. Now linear (2.0× per doubling): 40 KB 159 s → **0.39 s** (~400×), 100 KB ≈ 1 s. Validation behavior proven identical to HEAD across supported/contradicted/decimal/multi-claim/long-prefix/accented/Arabic cases (including answer correction). Rejected alternatives: narrowing the character class (measured still quadratic on letters/words/newlines — not digit-specific) and input truncation (complexity unchanged below the cap). 39 permanent tests in `tests/test_verification_security.py` (14 adversarial payloads incl. Arabic/RTL/Arabic-Indic digits/control chars, a best-of-N scaling-ratio guard, a structural leading-capture guard proven non-vacuous against HEAD, and behavior-parity tests).
- **Known pre-existing quirk, NOT fixed (out of scope)**: `extract_numeric_claims()` maps the metric `"passes"` to `"passe"` rather than `"passes_attempted"` — `"passes".rstrip("s")` yields `"passe"` while `metric_map` only has the key `"pass"`. Identical before and after the security fix; pinned as measured behavior in `tests/test_verification_security.py`.
- **OPEN (latent, pre-existing, not introduced by Step 6) — `resolve_output_dir()` does not validate competition/season IDs**: passing strings builds a traversal-shaped path (`resolve_output_dir("../../../etc","passwd")` → `output/competitions/../../../etc/passwd`, reproduced). **Not reachable today**: every CLI entry declares `type=int` on `--competition-id`/`--season-id`, and Streamlit sources them from the curated dataset catalog. `src/artifacts.py` was untouched by Step 6. Fix if a non-CLI/untrusted caller is ever added: coerce/validate to int in `ArtifactPaths`/`resolve_output_dir`.
- **OPEN (pre-existing) — BM25 index is persisted and loaded via `pickle`** (`04_vector_representation.py` writes, `src/retrieval/search.py` reads). Unsafe deserialization if the artifact is ever attacker-supplied; today it is generated locally by the owner's own pipeline. Not introduced by Step 6.
- **Checked clean in Step 6's knowledge pipeline**: no eval/exec/subprocess/shell/SQL; no document-controlled filesystem paths; regex paths linear (worst 0.019 s on 100 KB across preprocessing + sentence splitting + tokenization); chunk output bounded at 1.03× input (overlap only); raw document text is normalized/split/embedded and never interpreted as instructions.
